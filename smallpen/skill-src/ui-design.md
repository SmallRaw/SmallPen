# Application design

Use SmallPen for either complete editable screens and prototype flows, or reusable components and page parts that an AI composes with task-specific content for preview. Both use the same definitions, design rules and native renderer. Application implementation belongs to the later development task.

## Choose the requested deliverable

For a complete design, save the requested pages, states and prototype links. For a component system, deliver the requested Tokens, components, variants and reusable page parts; business pages are optional. For a composition preview, reuse that system, write the content and layout as a page in a copy of the package, and render it there; change the source package only when the user asks to save. These uses can be combined in one project. Infer the requested result from the brief; ask only when the choice changes what the user receives.

Read this Skill for the process, the installed CLI help for the file format and commands, and the project's actual specifications for business and visual rules. A Skill is not a second copy of those specifications. Follow existing specification locations, including records in the package and documents in the repository. Keep one authoritative body for each rule and link to it from the design notes. If a required source cannot be read or a behavior is undecided, report that explicitly rather than infer it from a screenshot or a component name.

## Understand the project

On first use, establish what software the user wants, who uses it, the core tasks and content, the expected platforms, and which platform to deliver first. Ask about missing choices that affect scope, structure or behavior. Use answers already supplied; a complete brief can proceed without another approval round. Bundle related questions. Keep the user's language unless the project requires another one.

Inspect an existing package and the project's design conventions before adding definitions. Use the project's existing design entry document; otherwise maintain one `DESIGN.md` alongside the package. Update it rather than creating a file each round. Record the requested deliverable, links to confirmed requirements, the first platform, capabilities each platform must preserve, style direction, shared definitions, justified structural differences and review targets/combinations. Do not duplicate an existing business specification's body. Treat user choices about page reuse, theme control and authoring tools as acceptance requirements. Mark assumptions and sample data. Missing key requirements require questions; ordinary visual details can be chosen and recorded.

## Tokens, components, then pages

Work in files, by name. Tokens and theme options live in `tokens.css` (`:root` for base values, `:root[data-viewport="tablet"]` for an option), shared components in `components/<Name>.html`, business pages in `pages/<Module>/<Page>.html` with `.mobile`/`.tablet` versions, and links as `data-click` on the trigger element. Bind a Token with its class (`bg-brand`, `gap-4`, `rounded-md`, `type-label`). UI text can use `string` Tokens through `data-text`; `boolean` Tokens through `data-visible` control visibility. Edit the smallest part that needs to change, then run `check`.

Place UI elements with `flex` containers, and use `grid` (`grid-cols-[240px_1fr]`, `col-span-2`) for real two-dimensional layouts such as card galleries and dashboards; use `left-[x] top-[y]` only for free placement inside a container without `flex` or `grid`. Crop a photo to a shape with `<div data-shape="mask">` on a page: its first child is the shape (an avatar circle), the rest is cropped to it. Keep task-specific geometry literal where it is a design rule, such as a logo. The CLI maintains the native component catalog and system views; do not write duplicate component showcase pages. Keep business pages on one canvas unless the user asks for another (`data-canvas` on `<body>`) or the modules are clearly separate. Links and prototype flows work only within one canvas; an element inside a copy links with `data-click` on its override element inside `<sp-use>`.

The bundled font covers Latin only. For Chinese or another script, copy a font file into `assets/fonts/`, declare it with `@font-face` in `tokens.css`, and bind its family through a `--font-` or `--type-` Token. Give sibling elements and each kind of project object distinct names; `check` reports duplicates.

Each weight/style is one TTF, OTF or WOFF file with its own `@font-face`. App and CLI derive other formats in a system cache outside the package; reading and rendering never change the package. WOFF2 is unsupported (`unsupported_font_conversion`).

Read existing theme groups, raw Token definitions and components. Define the needed shared vocabulary before drawing pages: typography, colors, spacing, radii, borders and useful reusable dimensions. Groups are project-defined; do not require a platform, language or light/dark group. Add a platform group only if this project's value differences need it. Create or reuse Tokens, then bind them when creating components and nodes. Check actual bindings; an inventory of unused Tokens is not a design system. Do not leave binding work for the developer.

Default to content-driven height. Height Tokens describe intentional shared constraints, such as a control size, touch target or editor viewport. Text, list, card, section and page heights follow content, line height, padding and gaps; use supported hug/content sizing for them. Do not generate a height Token per node, page, path or sample string, or rename those measurements into a large set of "semantic" sizes. If a renderer cannot compute content height, report that gap and verify the supported renderer; do not hide it by binding every measured height. Remove obsolete content-height bindings before deleting their Tokens, and check that widths, wrapping and required content still work.

Check both the Token's type and its binding target: `check` reports a class whose Token has another type. Keep shared paint bindings in the component, or override the intended part inside `<sp-use>`. A clean check or CLI PNG does not prove that the App can resolve the binding before expanding copies.

Build shared navigation, headers, inputs, actions and business-content components, then compose their instances on pages. Express component states, sizes and suitable structural alternatives as variants of one component. Labels such as Save and Cancel use copy text overrides (`<sp-use component="Button"><p data-name="Label">Save</p></sp-use>`) rather than separate component definitions. Compose standard shell parts and content copies in a page container. A copy has no arbitrary content slot: its children only override named parts.

Try a composition by writing the page, running `check`, and rendering it with `view --page NAME --as png` (`--theme` and `--scale` select the preview). To try something without touching the source package, copy the package folder and work in the copy. Read temporary artifacts within 30 minutes or copy them to retained paths.

## Complete screens and prototype flows

List the requested screens, states and navigation branches from the business specification. Compose a representative screen using shared definitions, inspect it, then reuse those definitions for the remaining screens. Keep required content and actions in each requested state. A destructive action needs confirmation or retry only when the specification requires it; do not invent a business rule to fill a blank.

Mark flow starts with `data-flow` on `<body>` and link the actual named trigger elements with `data-click` (or `data-hover`, `data-press`, `data-mouse-enter`, `data-mouse-leave`, `data-after-delay` for other triggers). Open menus, dialogs and sheets as overlays of their own small page: `data-click="overlay:Menus/Main; position: top-right; close-outside"`; close them with `close-overlay`. Keep connected pages on the same canvas. Search the page files for `data-flow` and the trigger attributes to compare saved starts, triggers and destinations with the requested branches, including cancel, return and error paths when specified. Follow the requested navigation in the App when delivering an App-reviewed clickable prototype. Report saved-link checks separately from navigation actually exercised; neither proves backend behavior.

After a scoped edit, read the affected copy overrides, links and rendered state again. Preserve unrelated choices, stable elements and the shared definitions. Deliver the saved package, design entry document, requested retained exports and the specific branches and combinations checked.

## Components and content previews

Start from the system's existing Tokens, component names, property domains and editable fields. Decide whether a difference belongs to a shared Token, a reusable variant, a copy text/property override or page content. Do not multiply component variants for changing labels or records. Build a small representative slice before expanding the library.

Represent reusable page structure with named parts such as navigation, header and actions. Compose them around business content in ordinary page containers. A copy exposes only its supported overrides; a page part is not an arbitrary content slot. If the requested structure needs a new shared component or a different ownership boundary, make that change explicitly within the authorized scope.

For preview-only work, copy the package folder and write the composition and sample content as pages in the copy. Run `check` and `view`; inspect the specification, wireframe and PNG, adjust the files and render again. Do not save sample pages to the source library. Check both representative and long content at the requested widths and combinations. Keep shared definitions unchanged unless their maintenance was requested. A render failure leaves this candidate unaccepted; fix the input or the supported definition and rerender.

Retain the final preview files and requested artifacts before temporary cleanup. Record the source package revision, selected components/variants, themes, review results and unresolved limits so another AI can reproduce the preview. The PNG, specification and wireframe must describe the same layout hash. If saving is requested, run `changes --since` on the source package first, then copy the pages in and run `check`. Rendering with a temporary theme does not save that selection.

Review reusable components before propagating them. Cover applicable default, hover, focus, selected, disabled, loading and error states. Check standalone components, nested copies and actual page overrides; a focus outline can fit the source component yet fail after its parent resizes. Use representative long names, paths, multiline descriptions and action combinations. Give title, secondary text, source, status and actions distinct roles and enough room. Check padding, baselines, alignment, readable text and action targets against the project's conventions. A dense list should reduce wasted space without forcing labels into vertical fragments or hiding required actions.

For a new package, run `init`. It creates `index.html` and an empty `tokens.css`; it does not decide the business requirements, theme dimensions or platform page versions. Write the first requested design explicitly.

## Adapt the same content

Deliver the agreed first platform, then assess the later platforms against the same business content and capabilities. Do not automatically create Desktop and Mobile copies of every page.

Use the smallest change the requested difference needs:

1. Keep the same page/content structure and use Token combinations for bound value changes: widths, heights, padding, gaps, type and color. Set the values for the chosen project groups. Check the same page with the appropriate explicit combination.
2. Use component variants for local reusable structural differences that values cannot express. A Token combination does not automatically select a component variant.
3. Add a platform version file or separate page only when the overall structure or interaction differs substantially and cannot be expressed through the shared design. Record the reason and preserve shared components and content.

Boolean Tokens can control `visible`; Tokens do not switch layout direction or node trees, and theme selection does not select a component variant. Consult `help rules format`, `help rules classes` and projection diagnostics before relying on layout support. If required behavior exceeds tool support, report the specific gap and resolve the affected design choice using existing requirements where possible; ask only when a user decision is needed. Do not silently duplicate full pages or omit functionality to pass a check. A smaller viewport does not authorize deleting fields, actions or access to full content.

Sizes allow only what the App allows: `w-[240px]` or a size Token fixes that axis, `w-full` fills a flex parent (not one that hugs that axis), and `w-fit` follows content on a flex container, a copy or a text. Min/max sizes apply only to an axis that fills. `check` refuses other combinations as `layout_not_in_app` and says what to write. This also applies to component copies. A part override inside `<sp-use>` takes a fixed size only.

A new flex component copy can default to content sizing when width or height is omitted. Read the selected variant's sizing constraints before composing it. Carry required shared dimensions explicitly, for example `h-control` (a `--size-control` Token) for a control whose height must stay 40 px; use `w-full` or `w-fit` for axes intended to adapt. After changing a variant, check that retained instance sizing still suits that variant. Do not assume the source's fixed dimension or Token binding automatically constrains a new copy, or change the shared rule to match an accidental hug result.

For responsive work, choose the requested small, medium and large review widths from the project's needs. Check the same agreed page version with each explicit theme combination. A separate mobile version passing a check proves nothing about the original version under a small-width theme. Width reduction alone does not adapt a sidebar, long path or action row: decide how each region fits and preserves access. Review density and hierarchy at larger sizes too; avoid excessive empty space or stretched actions. A handful of theme widths is a design sample, not proof of responsive behavior at every width in a production app.

## Inspect and deliver

Use `view` by name, scoped to the Tokens, component, variant, page, platform or element you need. Use `text` to navigate, then **specification** (`--as spec`) for implementation and provenance, **wireframe** for spatial questions, and **PNG** for high-fidelity visual acceptance. These are three views of the shared native layout, not substitutes for each other. Specifications separate authored constraints from actual bounds; preserve fill/hug, inspect field-level Token sources and copy overrides, and read node diagnostics. Expand one `--element` for fonts, colors, borders and declared interactions. A missing rule or measurement is unknown, not an inferred default. Match `layout.hash`, revision, size, themes and state; use `export --format png --evidence` for all three outputs from one solve. `view --as issues` and `check --render` report layout, text and contrast checks; `check --render` checks every page version or component variant in its selected scope unless one is named, and its findings never fail the check. Pass explicit `--theme group/option` values for each agreed combination; omitting them uses project defaults. Validation progress uses JSON lines on stderr; stdout stays the final result. The default per-target limit is 30 seconds (`--target-timeout` takes milliseconds). On Ctrl+C, read completed findings and `coverage.remaining`; exit code 130 and `interrupted` mean the remaining targets are untested.

Treat final acceptance as three separate checks:

1. **Data and coverage:** run `check`, then check Token references, binding targets, shared instances, preserved content/actions and prototype links. Run layout/text/contrast checks for the agreed targets and combinations. Read issues, skipped checks and unsupported layout diagnostics. If a whole-package check is too costly, use scoped checks that cover the same targets; count actual page versions and variants, not just report groups. Do not turn an interrupted or partial check into a pass.
2. **Visual review:** inspect the requested pages and relevant component states at a legible scale in each agreed size/theme combination. Look for clipping, bad wrapping, misaligned text/actions, oversized gaps, stretched controls and missing focus borders. Verify that text wraps and its parent grows in the actual renderer; several hugging texts in a row do not share available room automatically, so give the intended flexible text `w-full` and check the result. Use long content as well as sample labels. Fix defects in the shared component or Token before applying page-specific patches.
3. **App opening:** for a package intended for App review, actually open the final saved package in the App and confirm that the workspace loads and affected pages render. When the user requires CLI authoring, use the App only for permitted inspection. CLI validation and exports do not replace this check. If App access or visual inspection is unavailable or prohibited, continue the checks and repairs you can perform and state the remaining verification explicitly; do not present the package as fully accepted.

Tie every result to the saved package revision or the preview copy's revision, page version, variant and explicit themes. For a preview-only copy, native render evidence and visual review are the acceptance scope; opening it in the App means opening the copy, not the source package. After a final edit, rerun affected checks and refresh affected exports; retain older report revisions and identify unchanged-scope evidence instead of relabeling them. Record completed combinations and remaining gaps in the design entry document. Zero reported issues does not mean complete coverage, visual quality or a working App.

When CLI/App appearance must agree, compare exports with the actual App renderer at the same revision, themes, scale and device pixel ratio. Cover the requested pages and relevant variants. Check that opening and measuring the design leaves its revision unchanged. Record renderer errors, differences and unsupported coverage; do not report pixel identity from data checks alone. SmallPen maintainers can run `npm run test:render-parity` from `smallpen/` after building the frontend to check shared paint/layout semantics in CLI, SVG and WebGL.

People review the design in the SmallPen App and may fix small things there; the App rewrites the files it changes. Keep the latest `revision` any command reports; before writing code or continuing the design, run `changes PACKAGE --since REVISION` to read, by name, what changed (Tokens with old and new values, component variants and elements, page elements, links) and align your code and notes with it.

`changes --since` compares the files of the revision you saw, kept in a machine-local cache outside the project, with the current files; it works however the files changed. Revisions older than 7 days or evicted by the OS report `unknown_revision`: read the current design instead of assuming no changes.

Connect the requested clickable elements, triggers and destinations. Use explicit prototype steps to verify navigation. Distinguish page transitions from working input, real data saving or a finished application.

Deliver the requested saved package or preview copy and retained artifacts, the targets/combinations actually checked and material limits. Fix known opening failures, overflow, clipped required content and broken shared instances before calling the requested design complete. Describe the achieved result and verification; do not promise a perfect design from this Skill or from zero checker issues. Keep the project's specification links and design entry current. Temporary inspection files are not final deliverables. This Skill is independently installable and needs no sibling SmallPen Skill.
